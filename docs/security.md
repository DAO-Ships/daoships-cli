# Keystores and execution boundaries

The CLI encrypts account keys with quais' Web3 Secret Storage V3 implementation: AES-128-CTR, a keccak256 MAC and scrypt with `N=131072, r=8, p=1`, fresh salt and IV. Encrypted V3 JSON is stored in `keystore:<name>` documents in `state.sqlite`. Public profiles contain the account address and `kind: keystore`. Encryption happens before the atomic database transaction, so interruption or a settings conflict cannot leave a half-imported account. Encrypted backups are ordinary V3 JSON files and can be imported by compatible wallets.

Keystores are untrusted input. Validation bounds file size, key/cipher/IV/MAC lengths, salt length, KDF memory and work, and rejects ambiguous field capitalization before decryption. Scrypt workspace is limited to 256 MiB with at most four times the default work. PBKDF2 imports accept SHA-256/SHA-512 with 600,000–2,000,000 iterations. Lower-cost imports require an explicit flag and are immediately re-encrypted using the default scrypt strength. Oversized KDFs are never accepted. Only an account key is imported; mnemonic extensions are discarded.

The state directory requires mode 700 and the database requires mode 600 on POSIX systems. Secret input files must belong to the current user and have owner-only permissions. Reads use `O_NOFOLLOW`, inspect the opened descriptor and enforce a byte bound even if a file grows during the read. Symlinks, hard links, FIFOs and directories are rejected. The private parent directory protects SQLite's WAL and shared-memory files. These checks assume the operating system, current user and ancestor directories are trusted; Windows permissions use the operating system's ACLs.

Hidden prompts send output to stderr, disable password-reveal shortcuts and clear on completion. JSON stdout remains one machine-readable envelope. Agent flags carry paths to password/key files, never secret values. Secret operations run in a short-lived child when launched from the TUI, with terminal ownership released by Ink. The parent does not load or decrypt keystores. A shell that supplies plaintext environment variables already places them in process memory; migration/import are the only CLI operations that consume those values.

JavaScript strings and quais signing objects cannot be reliably wiped. We clear owned file-read and generation buffers, but do not promise heap-dump resistance or secure deletion. Use a strong password and protect backups. Changing a password does not revoke old backups, filesystem snapshots, or residual encrypted SQLite/WAL pages. Local deletion cannot erase SSD history. The database never intentionally stores plaintext keys or passwords, and signed transaction bytes are never journaled.

Read-only commands and previews do not unlock an account. Signing verifies the decrypted address against both the selected profile and reviewed sender. Actual chain-ID checks, SDK simulation, review hashes, value/gas limits and canonical receipt checks protect execution. DAO proposal, vault and token outcomes are checked beyond the outer receipt status. These checks cannot prove that arbitrary contract semantics match a user's intention; inspect calldata, events and follow-up state when using generic methods.

The recovery database coordinates all CLI processes sharing its directory. It cannot coordinate another wallet application or a second state directory. Broadcast uncertainty retains the account reservation and never causes automatic replay. Native CREATE stores its signed hash before broadcasting. Ordinary sends use the published SDK recovery protocol; an acknowledgement lost before a hash is saved can require a bounded replacement scan or independently obtained hash. Confirmation depth is configurable and is not a guarantee against future reorganization.

Release checks cover real encryption, hostile inputs, cross-process CAS, process death, nonce reservations, simulated broadcasts and receipt failures, terminal masking/cancellation, package contents and Node 22/24/26. Public RPC/indexer reads have been validated on Orchard and mainnet. A separate funded Orchard acceptance run confirmed one zero-value self-transfer through an encrypted wallet, journal recovery and no replay of its operation ID. The automated suite never consumes a funded private key. Every DAO/navigator mutation has not been repeated through the CLI on live contracts. This engineering audit is not an independent security certification.
